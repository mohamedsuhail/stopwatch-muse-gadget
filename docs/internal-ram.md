# Internal RAM on the StopWatch: where it goes, how to win it back

Written 2026-10-22, read-only analysis of the 10:03 build (`9bdeae4`) in
`.sdk/muse-gadget-sdk/esp32/build-muse-m5stack-stopwatch` (`esp_idf_size` on `muse-gadget.map`,
the effective `sdkconfig`, and the SDK source). Nothing was built, flashed or measured on the watch.

The heartbeat's `min=` (lowest free internal heap since boot) is about 5–6K, against 23K this
morning. Below that, Wi-Fi, TLS handshakes and BLE start failing to allocate.

## Where internal RAM goes

The ESP32-S3 has 341,760 B of DIRAM (internal RAM shared by code and data). The 10:03 build uses
170,313 B of it before the heap starts. Everything else comes out of the remaining ~171K at runtime.

### Static (linked), 170K

| What | Bytes | Notes |
|---|---:|---|
| IRAM code (`.text` + vectors) | 111,691 | the biggest single block |
| — BLE controller (`libbtdm_app.a`) | 16,954 | `CONFIG_BT_CTRL_RUN_IN_FLASH_ONLY` is off |
| — hardware support, FreeRTOS, heap, PHY, ringbuf, PSRAM, MSPI | ~42,000 | needed in IRAM; leave it |
| — SPI flash functions (`libspi_flash.a`) | 11,471 | `SPI_FLASH_PLACE_FUNCTIONS_IN_IRAM=y`, only switchable with flash auto-suspend |
| — **esp_new_jpeg** (`.iram1`, prebuilt) | 6,313 | **new today** with the 24 fps decoder |
| — SPI master driver and HAL | ~13,000 | `SPI_MASTER_ISR_IN_IRAM`, the display's QSPI |
| `.data` + `.bss` | 58,622 | |
| — `libmuse.a` | 21,937 | `s_rx` 4,104 (Gemini TTS read buffer); audio `buf` 2,880 + stereo 2×1,280; avatar maps `s_src`/`s_wt`/`s_deltas` 2,112 (new today) |

The Wi-Fi IRAM options (`ESP_WIFI_IRAM_OPT`, `RX_IRAM_OPT`, `SLP_IRAM_OPT`, `LWIP_IRAM_OPTIMIZATION`)
are already off. mbedTLS (`MBEDTLS_EXTERNAL_MEM_ALLOC`), NimBLE (`MEM_ALLOC_MODE_EXTERNAL`), LVGL
(`muse_lv_mem.c`), the LVGL draw buffers (`use_psram`), the avatar decoder and its stack, and the
Gemini TTS worker stack, queue and SSE buffer all live in PSRAM already.

### What most likely sets `min=`

`min=` is a low-water mark, so it records the worst moment, not the steady state. The static
growth today is about 8.5K (esp_new_jpeg 6.5K, avatar maps 2.1K). The other ~9K of the drop most
likely comes from a transient: **Wi-Fi RX buffers held under a full TCP window while Gemini TTS
streams**.

The TTS worker blocks in `xStreamBufferSend()` (`muse_gemini_tts.c:334`) whenever playback is
behind. Gemini sends faster than real time, so the connection's 16K receive window
(`LWIP_TCP_WND_DEFAULT=16384`) fills. That data sits in internal Wi-Fi RX buffers until the worker
reads again. The 24 fps avatar shares a core with UI and audio (`MUSE_UI_CORE == MUSE_AUDIO_CORE`),
so the readers drain more slowly and more buffers stay held. The Noise tunnel's socket can hold
another window at the same time.

The kept TLS connection itself costs almost no internal RAM: its mbedTLS buffers (~33K) are in PSRAM.

To confirm this before changing anything, compare `int=` against `min=` in the heartbeat while
idle and while speaking. A steady `int=` near 20K with `min=` near 5K points at the transient.
Logging `min=` from inside `put_pcm()` would pin it to TTS.

## Applied and measured (13:03 build with xAI TTS)

The four changes below are in the shared SDK and in `patches/0001` (regenerated by the xAI TTS
session). They were flashed in that session's build, which also has xAI TTS and the clip crossfade.
Static DIRAM: 170,313 B before, 166,201 B with these changes alone, 166,505 B with xAI included.

Heartbeat on the watch, avatar playing at 24 fps:

| | `int=` (free) | `min=` (low point since boot) |
|---|---:|---:|
| This morning | | 23K |
| Before these changes | | 5–6K |
| After, idle with Gemini key only | 44K | 18K |
| After, 4 xAI replies (up to 6.1 s of speech, kept and resumed TLS connections) | 39K | 18K |

The 18K low point is set during boot (Wi-Fi, tunnel and TLS handshakes) and didn't move while the
watch spoke. The xAI connection holds about 5K of internal RAM while it stays open. Replies are
short by design (the prompt asks for short spoken answers), so these runs cover normal use. A long
monologue was not tested.

The changes:

- `CONFIG_ESP_WIFI_DYNAMIC_RX_BUFFER_NUM=16` (was 32): caps the Wi-Fi receive backlog at ~26K.
- `adapter_cfg.stack_in_psram = true` for the LVGL adapter task: 8K of stack out of internal RAM.
- `EXT_RAM_BSS_ATTR` on the Gemini TTS `s_rx` buffer: 4,104 B (confirmed in the map).
- The Gemini speech buffer `s_tts_pcm` is 16 s instead of 4 s (512K of PSRAM), so the TTS worker
  keeps reading the socket rather than leaving the stream in Wi-Fi's internal buffers.

**The TCP window stays at 16384.** The SDK refuses any other value on tunnel boards
(`cmake/validate_config.cmake`: measured for the tunnel's DMA headroom). The larger speech buffer
covers the same backlog from the app side.

If the low point needs to go higher, items 4–6 below are next. The biggest, moving `noise_ctrl`
and the other app stacks to PSRAM, would also lift the boot-time low point.

**Logging without a restart:** opening the port with pyserial's DTR and RTS both forced low reset
the chip (`rst:0x15 USB_UART_CHIP_RESET`). miniterm and `tools/muse/chat.py` open it with the
defaults and don't.

**Building here:** `~/Documents` is synced by iCloud, which evicts build files (`dataless`) and
makes `cmake_depends` hang; the `* 2` files in the build folder come from the same sync. Building
in a folder outside `~/Documents` avoids it.

## Changes, ranked by savings against risk

Every SDK change goes into `patches/0001-stopwatch-customizations.patch` (README, "Changing the SDK
patch"). The sdkconfig lines go in `esp32/devices/sdkconfig.muse-m5stack-stopwatch`.

| # | Change | Expected saving | Risk |
|---|---|---|---|
| 1 | **Cap Wi-Fi buffering**: `CONFIG_ESP_WIFI_DYNAMIC_RX_BUFFER_NUM=16`, and keep the TTS worker reading (bigger speech buffer). A smaller TCP window is not allowed by the SDK | up to ~25K off the worst case (directly raises `min=`) | Low. Slower bulk downloads (OTA, images). Leave `RX_BA_WIN` at 16: IDF's Kconfig help says that is the minimum for good AP compatibility when Wi-Fi memory prefers PSRAM. |
| 2 | **LVGL adapter stack to PSRAM**: `adapter_cfg.stack_in_psram = true;` in `board_m5stack_stopwatch.c:615` (the adapter supports it, `esp_lv_adapter.c:696`) | 8K | Low. With `SPIRAM_FETCH_INSTRUCTIONS` + `SPIRAM_RODATA` the flash driver never disables the cache (`SPI_FLASH_CACHE_NO_DISABLE` in `spi_flash_os_func_app.c:32`), so PSRAM stacks are safe here, the same reason the avatar decoder's stack works. Stack accesses may be slightly slower. |
| 3 | **Gemini TTS read buffer to PSRAM**: `EXT_RAM_BSS_ATTR` on `s_rx` (`muse_gemini_tts.c:76`) | 4K | Very low. `ALLOW_BSS_SEG_EXTERNAL_MEMORY` is already on. |
| 4 | **Smaller LVGL draw-thread stacks**: `CONFIG_LV_DRAW_THREAD_STACK_SIZE=4096` after checking their high-water marks, or `CONFIG_LV_DRAW_SW_DRAW_UNIT_CNT=1` | 8K | Low to medium. Overflow if a draw task goes deep (masks, big text): measure first. One draw unit halves software-render parallelism, which may show at 24 fps. |
| 5 | **Other app stacks to PSRAM** with `xTaskCreate…WithCaps(…, MALLOC_CAP_SPIRAM)`: `noise_ctrl` (then drop `reserve_stack()`), `muse_keep`, `muse_input`, `muse_serial`, `tun_tx` | ~30K | Medium. Delete these tasks with `vTaskDeleteWithCaps`. Tasks that touch ISRs or tight audio timing stay internal. More code to change and test. |
| 6 | **BLE controller out of IRAM**: `CONFIG_BT_CTRL_RUN_IN_FLASH_ONLY=y` | ~17K static | Medium. Its usual danger (no BLE while flash is erased) does not apply because the cache stays on, but controller code then runs through the 32K instruction cache from PSRAM. Test BLE pairing and provisioning while the avatar plays. |
| 7 | **Smaller always-internal threshold**: `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=2048` | unknown, likely a few K | Medium. Moves 2–4K allocations (cJSON, HTTP headers, small buffers) to PSRAM. A driver that malloc()s a DMA buffer without `MALLOC_CAP_DMA` would break. |
| 8 | **esp_new_jpeg out of IRAM** with a linker fragment for its `.iram1` sections | 6.3K static | Medium to high. The library is prebuilt, so it needs a custom `[sections]`/`[scheme]` fragment. Its IDCT gets slower. Do it only if 1–6 aren't enough. |
| 9 | SPI flash functions out of IRAM | ~10K static | Not available as is: the Kconfig only allows it with `SPI_FLASH_AUTO_SUSPEND`. Skip. |

Changes 1–4 are a few lines each and together should win back about 20K at the worst moment plus
about 20K of steady headroom. That is enough to get `min=` above this morning's 23K without the
riskier items. After each step, check the heartbeat (`int=`, `min=`, `dma=`) over a few spoken
replies with the avatar running.
